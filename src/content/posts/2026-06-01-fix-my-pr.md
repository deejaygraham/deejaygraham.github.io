Or "How to Update a Feature Branch From main and Still End Up With a Single Commit PR". You create a 
feature branch, make a few changes, and push it to GitHub. By the time you open a pull 
request or have it reviewed, GitHub says the branch is several commits behind `main`.

If your repository expects exactly one commit in each pull request, you need to be a bit careful 
when syncing your feature branch with the latest main branch.

I constantly forget how to do this, so as usual, it's now a blog post as a practical reminder 
for future-me: how to take an existing branch and bring it up to date with main, continue 
working, and then make sure the PR still shows as a single commit.


## The Problem

Suppose the repository looked like this when the feature branch was created:

```text
A---B  main
     \
      D  my-awesome-feature
```

Commit `D` contains your work. While you are working, other pull requests add commits `C` and `E` to `main`:

```text
A---B---C---E  main
     \
      D  my-awesome-feature
```

Your branch now contains your work, but it does not contain `C` or `E`. GitHub describes it as being behind `main`.

A rebase takes the commits unique to your branch and replays them on top of the latest `main`:

```text
A---B---C---E       main
             \
              D'   my-awesome-feature
```

`D'` (D prime) contains the same intended changes as `D`, but it has a new parent and therefore a new commit ID. 
The resulting history reads naturally: the changes already merged to `main` came first, and your feature was added afterward.

## Rebase versus Merge

Both merging and rebasing can bring `main` into a feature branch, but they produce different histories.

Merging `main` into the feature branch normally creates an extra merge commit:

```text
A---B---C---E---------M  my-awesome-feature
     \               /
      D-------------/
```

This is valid, but it adds a merge commit whose only purpose is to catch up with `main`.

Rebasing produces a straight history:

```text
A---B---C---E---D'  my-awesome-feature
```

When the goal is for the pull request to look as though your changes were made from the latest `main`, rebasing is usually the clearer choice.


## Safety First

Before rebasing, remember:

1. Make sure your current work is committed or stashed.
2. Fetch from GitHub before deciding what is current.
3. Rebase your feature branch, not `main`.
4. Do not rebase a shared branch without coordinating with the other people using it.
5. If the rebased branch was already pushed, update it with `--force-with-lease`, never an unguarded `--force`.
6. Test the rebased result before pushing it.

## The Process

The commands below assume the primary branch is named `main` and the remote GitHub repository is named `origin`.

### Switch to your feature branch

Replace `my-awesome-feature` with your real branch name.

```powershell
git switch my-awesome-feature
git status
```

Confirm that `git status` names the expected branch. Rebase changes commit history, so checking the branch first prevents an avoidable mistake.


### Add uncommitted changes

```powershell
git add -p
git commit -m "A made some changes here"
```

`git add -p` lets you inspect and stage each change rather than automatically staging every modified file.

If the work is not ready to commit, temporarily stash it instead:

```powershell
git stash push --include-untracked -m "Stashing stuff to come back to later"
```

Restore it after the rebase with:

```powershell
git stash pop
```

### Fetch the latest GitHub state

```powershell
git fetch origin
```

Fetching updates remote-tracking names such as `origin/main`. It does not alter your working files or your feature branch.

### Inspect the divergence

```powershell
git status --short --branch
git rev-list --left-right --count HEAD...origin/main
git log --oneline --decorate --graph --boundary HEAD origin/main
```

For `git rev-list`, the first number is the number of commits unique to your feature branch, and the second is the number unique to `origin/main`.

For example:

```text
1    15
```

This example shows that the feature branch has one commit of its own and is missing fifteen commits from `origin/main`.

### Rebase onto the latest `main`

```powershell
git rebase origin/main
```

Git finds each commit unique to the feature branch, moves the branch to `origin/main`, and replays those commits in order.
If Git reports no conflicts, the rebase finishes automatically (I am not going to address conflicts here).

## Verify the rebased branch

Do not push immediately merely because Git says the rebase succeeded. Confirm the history and content:

```powershell
git status
git log --oneline origin/main..HEAD
git diff --stat origin/main...HEAD
git diff --check origin/main...HEAD
```

From this we can tell: 

- Is the working tree clean?
- Which commits will the pull request add?
- Which files will the pull request change?
- Are there whitespace errors?


## Push the rebased branch

If this is the first time the feature branch has been pushed, use a normal upstream push:

```powershell
git push --set-upstream origin my-feature
```

If an earlier version is already on GitHub, the rebase changed its commit IDs. A normal push will correctly 
be rejected as a non-fast-forward update. Use:

```powershell
git push --force-with-lease origin my-feature
```

`--force-with-lease` checks that the remote branch still has the version you most recently 
fetched. If someone else pushed new work after your fetch, the command refuses to overwrite it.
